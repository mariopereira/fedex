# Contributing

This package is a PHP interface to the FedEx APIs. It is meant to run on **PHP 7.4 and newer**, and everything below is written so that a change keeps it that way.

## Conventions

* **PHP 7.4 syntax only**, in `src/` and in the tests. No union types, named arguments, constructor property promotion, attributes, `match`, the nullsafe operator, or functions that came with PHP 8 (`str_contains()` and the like). `composer.json` asks for `"php": ">=7.4"` and has `config.platform.php` set to `7.4.0` on purpose, so that Composer cannot resolve a dependency that needs more. Code written for 7.4 must also run on newer versions without a deprecation.
* **Document every class, method, property and constant** with a docblock: the API documentation is generated from them (see "Documentation").
* **`schemas/` is the source of truth** for the FedEx requests and responses. Do not invent fields, endpoints or values that are not in a schema.
* **Do not change `composer.json`, `composer.lock`, the autoload rules or the dependencies** without discussing it first.
* **Keep the README true.** Its examples are tested (see below): when the public API changes, change the README in the same commit.

Some rules are enforced by tests, so that a change cannot break them by accident:

* **TLS is never weakened.** `TlsGuardTest` reads the code of `src/` and fails if an option of cURL that was not reviewed, a stream context, a change of the PHP settings or an address that is not `https` appears. Do not disable the verification of certificates to work around a problem: find the cause.
* **No test calls the live FedEx API, or the sandbox.** The tests use a fake transport, or the throwaway server on `127.0.0.1` of the loopback tests. Never send a real shipment, label, pickup or cancellation to test something.
* **Operations that change data in FedEx are never repeated automatically.** `FedexShip::create()`, `cancel()`, `createTag()` and `cancelTag()` are never retried, because repeating them could create or cancel a shipment twice. Only requests that are safe to repeat are marked as such, and the tests check each Ship operation.
* **Secrets stay out of messages.** Exceptions and logs must not contain access tokens, credentials, account numbers or the content of labels.

## Tests

The tests use PHPUnit 9.6, the last version that runs on PHP 7.4. Run them with the oldest PHP that the package supports:

```
composer install
composer test
```

Any notice, warning or deprecation fails a test, and so does a risky test (one without an assertion).

| Command | What it runs |
| --- | --- |
| `vendor/bin/phpunit` | the `unit` suite, without the `loopback` group (about twenty seconds, most of it the two `slow` tests) |
| `vendor/bin/phpunit --exclude-group slow,loopback` | the fast run, a couple of seconds. Name both groups: an `--exclude-group` on the command line replaces the exclusion of `phpunit.xml.dist`, so `--exclude-group slow` alone also runs the loopback tests |
| `vendor/bin/phpunit --group loopback` | the loopback tests only, under a minute |

* **The loopback tests** use the real cURL, `FedexAuth`, `FedexClient` and the API classes against a throwaway PHP server that listens on `127.0.0.1` only, which the tests start and stop themselves. They check what really goes on the wire: headers, timeouts, refused connections, retries. They need the `curl` extension and `proc_open`. Nothing leaves the machine.
* **The `slow` group** has two tests that break generated Ship requests thousands of times.
* **Some tests skip themselves on purpose**: the ones about file modes need a system that has them (not Windows) and a user they apply to (not root), and one test needs Windows. Run the suite on both kinds of system when you change `FileTokenCache`.
* **To check a newer PHP**, run the same tests with it. If that PHP has no `php.ini`, enable what it needs on the command line, for example `php -d extension=curl -d extension=mbstring vendor/bin/phpunit`.
* **New behaviour needs tests, and a bug fix needs a test that fails without it.** When you can, check that a test fails when the code is wrong: break the code on purpose, run the test, and put the code back.

The tests of the README (`tests/Unit/ReadmeTest.php`) parse every `php` example with the PHP that runs them (so on 7.4 an example that needs a newer PHP fails), and check that the classes, the constants, the methods, the number of arguments and the paths that the README names exist. They never run the examples.

## Documentation

The API documentation in `docs/` is generated by PhpDocumentor from the docblocks, and it is committed.

* PhpDocumentor does **not** run on PHP 7.4: use PHP 8 or newer for this step, with the extensions it needs enabled (it has been run with `curl` and `mbstring`).
* **Clear `docs/` first.** PhpDocumentor never removes the pages of classes that were renamed or deleted, so rebuilding over the old output leaves stale pages.
* Then generate it from the root of the repository:

```
vendor/bin/phpdoc -d src -t docs
```

The cache (`.phpdoc/cache/`) is not committed.

## What a release contains

The archive that Composer downloads is made from the files of the repository that `.gitattributes` does not mark with `export-ignore`. A release contains only `LICENSE`, `README.md`, `composer.json` and `src/`. The tests, the documentation, the schemas, `composer.lock`, this file and the editor and tool files are left out: `composer.lock` because Composer ignores the lock file of a package that is installed as a dependency, and it only pins the tools of development.

`tests/Unit/ReleaseFilesTest.php` fails when a new file or directory would go into a release, so that adding one is a decision: mark it with `export-ignore` in `.gitattributes`, or add it to the list in the test if it must ship. The test reads `.gitattributes`: it cannot see how Git matches a pattern, so to see exactly what a release would contain, run `git archive HEAD | tar -t`.
